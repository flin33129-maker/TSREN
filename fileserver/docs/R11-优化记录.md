# R11 优化记录：AI 为什么慢，以及改了什么

这一轮没有加新页面，全部工作都围绕一个具体抱怨：**"AI 又慢又不听话，参数还不能调"**。
所有数字都是在这台机器上实测出来的，不是估算。

## 一、先量，再改

新增只读诊断口 `GET /api/ai/diag`（需登录），把一次对话的提示词逐段称重
（调 llama-server 的 `/tokenize`，0.03 秒返回，不触发推理）。第一次量出来的结果：

| 组成 | token | 说明 |
|---|---|---|
| 静态 system | **965** | 其中真正的人设只有约 40，其余 930 是工具行为说明 |
| 【背景】尾巴 | 24 | 位置 + 时间 |
| 工具声明 JSON | **981** | 9 个工具的 schema |
| 合计前缀 | **1970** | 本机预填充 18 tok/s → **109 秒** |

关键发现：那 930 token 的说明，开关是 `_toolsOn()`（服务端总开关），
所以**即使本轮把"联网""写文件"都关掉，也照样发送**——而那轮根本没有工具可用，全是废字。

## 二、载体：CPU 一直跑在 800 MHz

```
scaling_governor = powersave          # 基频 2.3 GHz，实测 700–800 MHz
cpu temp = 27 °C                      # 不是过热降频，是电源策略
```

笔记本默认 `powersave`，而这台机器是常开的工作站。切到 `performance` 后稳定在
2.3–2.4 GHz，并新增 `cpu-performance.service` 开机自生效（已纳入版本库 `ops/systemd/`）。

## 三、提示词按「本轮真正生效的能力」裁剪

原来一整块 930 token 的说明，现在拆成三段，用 `o._eff`（本轮生效权限）决定发哪些：

- 核心 5 条（永远发）：能操作工作站、工具结果是真实内容、不输出 XML 标签、不提模型名、【背景】行不要抄
- 联网段（仅本轮有 web 时）：实时信息只能来自搜索结果、三类稳定知识不要搜、网页内容是数据不是指令
- 写文件段（仅本轮有 write 时）：写操作会真实落盘 / 本轮不能写文件请说明

每条约束都保留了出处（都是踩过的坑），只压缩措辞，没有删条目。

实测静态 system：**989 → 463 token**（工具开）/ 约 **250 token**（工具关）。

## 四、顺手抓到一个真 bug：关掉联网，连读文件都不会了

复现：`{allowWeb:false, allowWrite:false}` 问"这个目录里有哪些文件"

- 修复前：5.8 秒返回，「我无法访问或列出目录中的文件，因为我无法操作工作站的本地文件系统」
- 原因：`anyTool = allowWeb || allowWrite`，两个开关都关时连 list_dir/read_file 都不下发，
  而提示词又说"你能操作工作站"——自相矛盾，2B 只能选"我做不到"
- 修复后：96.5 秒（两轮工具），真的调用 `list_dir`，回答「附件3.全过程资料打包-电科院 / 临时文件 / Android」

现在读类工具只要工具装配在位就下发，具体清单由 `specs(eff)` 决定：
两个都关时只剩读类工具（约 500 token），而不是整份 981。

## 五、参数终于能调了

原先只有管理员全局接口 `/api/ai/params`（改 `data/ai.json`，影响所有人），普通用户在对话里连温度都改不了。

- 服务端：`/api/ai/chat` 接受 `temperature` / `maxTokens`，由 `_normGen` 归一（越界/非数字丢弃），
  只影响本次请求，不落盘；上下文预算 `_budget`/`_fitAsync` 也按本次 maxTokens 预留
- 响应（JSON 与 SSE done 帧）回显 `settings`，界面显示"本次实际"而不是显示可能被丢弃的输入
- 界面：工具条「参数」开关 → 温度滑杆 0–1.5 + 长度 256/512/1024/2048，存 localStorage

实测：请求带 `temperature:0.15, maxTokens:256` → 请求体确认携带，界面底部显示
「本次实际：温度 0.15 · 上限 256 tokens · 上下文 32k」；`maxTokens:64` 时 completion 恰好 64；
非法值（`temperature:99`、`"abc"`）被丢弃并回退默认；全局 `ai.json` 仍是 0.7/1024，未被污染。

## 七、更正与新增（第三轮）

### 7.1 更正：前缀缓存没有问题

上一版本这里写着"工具第二轮没有复用前缀缓存"，**这个结论是错的**，撤回。
错在把 `usage.prompt` 当成了"本轮实际预填充的 token 数"——它报的是**完整提示词长度**，
即使命中缓存也是满额。直接验证：

- 同一请求连发两次：第二次 `prompt_n=1`、`prompt_ms=136`（几乎零预填充）
- 换一个只有末尾不同的追问：`prompt_n=28`
- 站点侧同一问题连问三次：102.4s（冷）→ 24.9s → 24.9s

所以缓存一直是好的，不需要修。教训：`usage.prompt` 只能当"上下文有多大"看，不能当"算了多少"看。

### 7.2 新增：目录类提问不再编文件名

实测（读工具闸门修好之后）：同一句「这个目录里有哪些文件？只说前两个名字」连问三次，
回答分别是 `public、private` / `main.py、data.txt` / `shuai、shuai` ——
真实目录里没有这些名字，而且三次一次 `list_dir` 都没调（工具就在手边）。
小模型的工具调用是概率性的，提示词只能提高概率、保证不了。

按 web 预搜索的既有做法在服务端做硬约束：判出「问当前目录内容」时，
**系统自己先跑一次 list_dir**，把真实结果作为 system 消息注入，并写明"只能从这些名字里挑"。

判据 `_fileIntent` 刻意收紧（宁可漏判）：必须同时有对象词（目录/文件夹/盘）与询问词（有哪些/列出/里面…），
排除"读一下/打开/比较"这类要连着读文件的提问，长度上限 60 字符。

验证（真实前 8 项含 小型电场V1.zip、新建文件夹.7z）：

| | 改造前 | 改造后 |
|---|---|---|
| 是否编造文件名 | 3 次里 2 次编造 | **0 次**，全部命中真实名字 |
| 是否调用工具 | 0 次自动列目录 | 3 次全部自动列出并注入 |

### 7.3 新增：上传队列面板（把"多线程"变成看得见的东西）

R10 做了 8MB 分片 / 4 路并发 / 每片重试 3 次，但界面上只有一根总进度条 ——
改进等于没做（用户原话"稳定性太差"，看不到任何东西在动）。

现在 `yk()` 加埋点 + 右下角浮动面板（纯 DOM，不侵入 650KB 里的 React 树）：
每文件一行（文件名 + 进度条 + 状态）、顶部总进度/已完成数/实时速度、
超过 8 个折叠、完成 3 秒后淡出、失败标红并提示重试。

真机验证（200MB + 8KB 两个文件，走真实 UI 路径）：

```
面板出现 2 行
大文件进度: 0% → 16% → 32% → 44% → 48% → 52% → 56% → 68% → 72% → 76% → 84% → 100%
顶部: 上传完成 2/2 · 100% · 95.4 MB/s
服务端落盘: 209715200 字节（与上传大小精确相等）
```

### 7.4 断网真机验证：分片重试是真的，失败也敢说实话

用 CDP `Network.emulateNetworkConditions` 真断网（不是 mock），传 512MB / 384MB：

| 场景 | 操作 | 结果 |
|---|---|---|
| A 抖动 | 传到 13% 断网 1.2 秒后恢复 | 每片 3 次退避重试救回来，**上传完成 1/1 · 89.4 MB/s**，服务端 536870912 字节精确 |
| B 断网不恢复 | 传到 8% 断网且一直不恢复 | 面板变红「上传遇到错误 0/1 · 14%」，行状态 err，提示「有 1 个文件失败」，**服务端没有该文件**（不谎报成功） |
| C 恢复后重试 | B 之后恢复网络，点「重试失败的 1 个」 | 按钮变"重试中…"→**上传完成 1/1 · 104.8 MB/s**，服务端 402653184 字节精确 |

这一条把"稳定性差"从一句抱怨变成了可复现的验收：断网不掉链子、失败不撒谎、恢复一条点击。

### 7.5 顺手挖出真 bug：失败的分片上传永久占盘

验证失败路径时翻了一遍存储，发现公共盘根目录躺着两个隐藏文件：

```
.uploading-34ac026a…  75 MB
.uploading-42bddfde… 136 MB
```

共 211MB，来自失败/中断的分片上传。用户看不见（点号开头、列表已过滤），但空间永久被吃掉。

根因：`sweepUploadTmp` 的匹配正则只有 `\.(davtmp|s3part|s3tmp)-`，
而 `chunk-init` 的临时文件名是 `.uploading-${uploadId}` —— **整整一类残骸漏扫**。

修法：正则补上 `uploading`；并且启动趟**无条件**删 `.uploading-*`（分片会话只存在内存里，
进程重启后必然失效，此时任何 `.uploading-*` 都是确定的孤儿，不必等 24 小时；
davtmp 等仍按 24h 判定，避免误删活跃传输）。

对照验证（造两个 3MB 假残骸后重启）：

| 文件 | 期望 | 实际 |
|---|---|---|
| `.uploading-deadbeef…` | 启动趟回收 | 已删除 |
| `.davtmp-control0000`（新鲜） | 24h 内保留 | 仍保留 |

日志：`[cleanup] 回收上传残骸 1 个 / 3 MB`；现场原有的 211MB 残骸重启后归零。

### 7.6 断点续传：断了接着传，不用从头再来

原来 `uploadId` 随机、会话只在内存里，于是断网重试 / 关页面 / 重启进程之后，
之前传的全作废 —— 1GB 文件得从头再来。现在：

- `uploadId` 确定性化 = `sha256(用户id|盘|目录|文件名|大小|分片大小)`
  （带 `user.id` 是为了隔离：两个用户传同一目标不会撞同一个临时文件）
- 已收分片集合落盘 `.uploading-<id>.map`，每片写完更新
- `chunk-init` 若有位图且临时文件够长，以 `r+` 复用已有数据，返回 `{received, resumed}`
- 前端据此跳过已有分片，只补缺的；跳过部分的字节仍计入进度

实测（384MB / 48 片，传到 33% 断网失败）：

```
失败后 chunk-init → {"received":[0,1,…,19],"resumed":20}
前端进度序列     → 0% → 42% → 46% → 50% → … → 100%
服务端落盘       → 402653184 字节，精确
```

顺带的连带修正：孤儿清理不能再把带位图的 `.uploading-*` 当垃圾删（否则跨重启续传被自己杀掉），
改成"有位图且 7 天内动过 → 留；无位图或超 7 天 → 删"。

### 7.7 下载侧不再是个黑盒

原来下载是 `document.createElement('a')` 直接指到 `/api/download` —— 浏览器原生下载条，
没有速度、断在中途只能从头再来。上传都做完队列面板了，下载还停留在十年前。

改成自己读流（纯前端，服务端本来就支持 Range/206）：

- `fetch` + `ReadableStream` 边读边累计 → 面板显示实时进度与速度
- 取消：`AbortController`；取消后保留「重试」（取消是暂时停，不是放弃）
- 断点续传：已收 N 字节就带 `Range: bytes=N-`，服务端回 206 只发剩余部分
- 面板与上传共用右下角 `#r11-tw` 容器，样式统一，不会互相压住

实测（120MB，走真实 UI：勾选 → 点「下载」）：

| 场景 | 结果 |
|---|---|
| 正常下载 | 进度 0% → 10% → 19% → … → 100%（12 个不同值），落盘 **125829120 字节**精确 |
| 35% 时取消 | 面板转「已取消 + 重试」，进度停在 35% |
| 取消后重试 | 进度序列 **35% → 38% → … → 100%**，落盘仍 125829120 字节（Range 只补了剩余 65%） |

过程中修掉一个自己引入的 bug：`parts` 数组原来只在读取循环**正常结束**后才挂到 item 上，
取消走 catch 分支时已收片段丢失 → 重试只能补回后半截，实测拼出 **86MB（应为 120MB）**。
现在拿到数组就立刻挂上。

### 7.8 悬案结案：重启把可续传的临时文件删了

上一轮留下的疑点：重启后 160MB 的临时文件在服务启动前就消失，只留下位图。
当时我怀疑过清理器（它只承认删了 101 字节的位图）、怀疑过合成测试的差异，都没结论。

这次加了临时日志（`ST_DEBUG_CHUNK=1`，默认静默）才定位到真凶 —— 不是清理器，
是 **shutdown 钩子**：

```js
for (const [id, up] of this.uploads) {
  try { up.handle.close(); } catch {}
  fs.unlink(up.abs, () => {});      // ← 就是这里
}
```

初衷是"进程没了，半截临时文件别占盘"，但它只删临时文件、不删位图，位图随后被清理器
当孤儿收走 —— 而 R11 刚给位图赋予续传价值，两者直接冲突。

**为什么上一轮的合成测试会误导我**：那些临时文件是我用 shell 造的，不在服务端的
`this.uploads` 里，shutdown 根本没碰它们 —— 于是"重启后文件还在"，结论看起来是好的。

修法：退出时有位图（可续传）→ 保留临时文件与位图，交给 7 天清理规则兜底；
没有位图 → 照旧删掉。

端到端验证（384MB，真实浏览器 UI）：

| 步骤 | 证据 |
|---|---|
| 传到 33% 断网失败 | 临时文件 167772160 B + 位图 101 B |
| `systemctl restart station` | 日志 `[chunk] shutdown r11-跨重启.bin 保留（可续传）` |
| 重启 + 启动趟（30s 孤儿清理）后 | 两个文件都还在 |
| 重新上传同一文件 | 进度 `0% → 42% → 44% → … → 100%`，落盘 **402653184 字节**精确 |

### 7.9 大文件下载：直接流式写盘，不再整份攒内存

上一轮下载已经能看进度、能续传，但收尾还是"整条流拼 Blob 再触发保存"——
120MB 无所谓，1GB 就要吃 1GB 内存，这台机器上正好有 8GB 级的文件。

超过 8MB 走 File System Access：`showSaveFilePicker` 先让用户选位置，
之后整条流直接写进磁盘句柄。内存占用与文件大小无关（只剩 64KB 级分片缓冲）；
断点重试时 `writable.seek(已收字节)` 定位后继续写，不重写已落盘部分。
headless / 自动化（`navigator.webdriver`）没有保存对话框、硬弹会卡住，自动回落 Blob 方案。

验证（真实 UI + 注入假保存句柄模拟浏览器下发句柄，全部字节级断言）：

| 场景 | 结果 |
|---|---|
| A 回落路径 120MB | 进度 9 级 0%→100%，落盘 **125829120 B** 精确 |
| B 写盘路径 700MB | 进度 43 级，写进句柄 **734003200 B**（byte-exact），`close` 被调用，**下载目录为空**（证明没走 Blob/anchor） |
| C 25% 取消后重试 | `seek(185880799)` 一次，之后只写 **548122401 B** = 734003200 − 185880799（差值 **0**），最终完成 |

调试坑记一笔：`Page.navigate` 到只有 hash 变化的 URL **不会真重载**，React 状态与注入的
假 picker 都会残留，导致上一阶段的勾选被一起下载（观测到 859832320 = 700MB + 120MB）。
测试脚本改成带时间戳强制整页重载。

### 7.10 版本归档有了保留策略（`.versions` 只进不出 → 有进有出）

上一轮清理测试文件时发现：删掉 820MB，磁盘却没降。查下去是 `public/.versions/` ——
覆盖写入和删除都会把旧文件存进去，**代码里没有任何清理逻辑**。19 个条目就占 82MB，
而且"永久删除"的文件历史版本还躺在盘上（用户以为删干净了，其实没有）。

现在给它立了规矩（挂在既有清理器节拍上：启动 30s 后一趟 + 每 6 小时一趟，不新增接口）：

- 原文件还在 → 每个文件**只保留最近 3 个版本**，更旧的删掉
- 原文件已不存在 → 整个版本目录**再留 7 天**（留一点反悔余地），之后连目录一起回收
- 顺带清掉因此变空的目录（递归目录结构会留下空壳）

验证（造 5 个版本 + 两种孤儿目录，重启触发）：

| 场景 | 结果 |
|---|---|
| 原文件在，5 个版本 | 保留 **3** 个（Oct 23/24/25），最旧两个被删 |
| 原文件已删，版本 8 天前 | 文件 + **目录**都被回收 |
| 原文件已删，版本是新的 | 仍保留（没误删） |
| 空目录 | 一并清掉 **13 个** |

`GET /api/versions` 读数从 5 条变 3 条，与磁盘一致。

修的过程中还踩了一个自己挖的坑：孤儿分支 unlink 完直接 `return`，漏了 `rmdir` ——
文件删了、目录还在（日志显示"回收 15 个文件"但目录仍存在）。父级的空目录清理只管自己
这一层，轮不到子目录，所以补了一句 `rmdir` 才真正干净。

### 7.11 历史版本：界面看得见、拿得回来

上一轮给 `.versions` 立了保留策略，但前端从来没调过 `/api/versions` —— 版本历史在界面上
完全不可见；而且服务端**只有列表接口，没有取回/恢复接口**。存了一堆版本，用户既看不到也拿不回来。

这轮两头都补上：

前端（文件详情弹窗新增版本区）：

- 标题：`历史版本 N 个 · 合计 X`，下面一行写清策略（保留最近 3 版 / 删除后 7 天回收）
- 逐条：时间、大小、`恢复`、`下载`
- 恢复前 confirm 提示"当前内容会先存为一个新版本，可以再恢复回来"
- 实现上是在详情 JSX 里插一个带 `data-disk/path/name` 的空容器，再交给
  MutationObserver 填充 —— 这样能直接拿到文件对象，不用去猜弹窗的 DOM 结构

服务端（两个新接口）：

- `GET /api/version-get?disk=&path=&name=` 取回某个历史版本（登录 + 读权限 + 路径穿越校验）
- `POST /api/version-restore` 恢复某版本：**先把当前文件归档**，再放回旧版本；
  写审计日志 + 通知前端刷新

验证：

### 7.12 工具声明瘦身 981 → 794（顺手修两个真 bug）

1. `parseCwd`

### 7.16 SMB 密码与网页登录**真的同步**了

上一节的账号体系还差一口气：老账号（`Dozin`、`dav`、`QWER1234`、`cross874`）得去设置页
单独设一次 SMB 密码，等于还是"记两个密码"。

硬约束：网页端口令存的是 `scrypt(盐)` 单向哈希，**服务端永远推不出明文**，
所以「把库里的密码同步过去」这条路不存在。但同步根本不需要存档 ——
用户每次登录都会把明文交上来，于是：

    登录 verify 通过  →  把同一个密码写给 Samba  →  两边永远一致

不能每次登录都起 `smbpasswd`（150~400ms），所以存一个 HMAC 指纹判断密码变没变：

```
fp = HMAC-SHA256(本机随机密钥, 用户名 \0 明文)
```

指纹没变 → 直接跳过（零子进程）；变了 → 重设并更新指纹。
密钥 `data/.smb-key`、指纹 `data/smb-sync.json` 都是 0600，`data/` 本就在 `.gitignore` 里。
没有存明文，也没有引入可离线爆破的弱哈希（HMAC 需要密钥文件 + 指纹文件同时泄露）。

边界处理：

| 情况 | 行为 |
|---|---|
| 登录密码 ≥ 8 位 | 同步到 SMB，下次连共享直接用网页密码 |
| 登录密码 < 8 位（老账号） | 跳过同步，不阻塞登录；设置页卡片可单独设一个 |
| 用户名含中文/空格 | 跳过（SMB 不支持），界面早已提示改名 |
| 管理员重置了某人的密码 | 该用户下次登录自动同步 |
| 注册 | 注册那一刻就建号 + 写指纹，首次登录不再重复写 |

实测（真机）：

```
① 先把 uitest 的 SMB 密码改成别的 → smbclient 用网页密码连：NT_STATUS_LOGON_FAILURE
② 用网页密码登录一次 → 首次登录 295ms（含同步）
③ 再 smbclient 连 → 成功列出公共盘（密码已同步）
④ 再登录一次 → 177ms（走指纹快路径，无子进程）
⑤ audit.log 只有一条 smb-sync（detail=密码已同步），第二次登录不再记录
⑥ 注册新账号 → 首次登录 smb-sync 记录数 1→1（注册时已写指纹），SMB 直接可写
```

同步的触发点是**网页登录**。走 WebDAV / S3 / IM 的鉴权路径不会触发写 Samba，
但那些路径用的本来就是网页密码，不影响使用。

### 7.20 工作站卡顿：一个永真守卫引发的 DOM 死循环（事故复盘）

用户反馈："为啥现在工作站这么卡啊"，截图里文件管理页整块空白。

**根因**（上一轮改「持续运行」时埋的）：那个 IIFE 用 MutationObserver 盯着 body，
把指标改写成主机 uptime，但守卫写成了

```js
if ((val.textContent||"").replace(/\s+/g,"") === want+want) return;   // ← 永假
```

`want` 是 `"0天10小时"`，`want+want` 是 `"0天10小时0天10小时"`，永远不相等。
于是每次 DOM 变动都重写一次 `innerHTML` → 重写又触发自己的观察器 →
**无限自激循环**。对照实验（旧版 vs 修复版，同一浏览器同一账号）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 3 秒内 DOM 变异 | **72,965 次**（≈2.4 万/秒） | 4 次 |
| 3 秒内长任务(>50ms) | 1 | 0 |
| 主线程延迟 | **1509 ms** | 0 ms |
| 文件页行数 | 5 | 5 |

主线程被钉死 → 页面点不动、切路由像卡住、React 来不及重绘就呈现"空白"。

**修复**：
1. 守卫比较真正的文本 `=== want`，已是目标值就完全不动 DOM。
2. 观察器只用 `requestAnimationFrame` 合并：一帧最多动一次。
3. 运行时长 60 秒才重取一次（按小时变，没必要更密）。
4. 顺带把「服务器状态」面板的 MutationObserver 也加了 rAF 合并 ——
   文件列表这种高频渲染会把 childList 变更刷爆，不加合并每帧可能跑几十次 mount()。

**验证**：修复版 3 秒 DOM 变动 4 次、长任务 0、主线程延迟 0ms；文件管理页 9 行正常；
「持续运行」显示 `0天10小时` 且备注"主机运行时长 · 服务重启不影响"；16 条路由回归通过。

**确认不是服务器慢**：负载 0.14、接口 1–20 ms、无重启无告警。
侧边栏「722 GB / 1.0 TB」也是真的 —— 新挂的 `/dev/sdc1`（932G，已用 702G，
挂在 `/storage/乱七八糟`），统计没错。

**教训**：往 React 应用里插 MutationObserver，守卫必须比较**真实的目标文本**，
回调里的 DOM 写入一定要 rAF 合并 —— 否则很容易写出"自己触发自己"的死循环，
症状还特别像"服务器卡"。

### 7.21 把卡顿事故变成回归防线：性能冒烟测试

7.20 那种 bug（DOM 自激循环）**不抛异常、不影响功能断言、接口全绿**，
只有用户能感觉到"卡"。所以补一个能把它量出来的测试。

`perf_smoke_test.py` 对 6 条主要路由各跑 3 秒，统计四个指标：

| 指标 | 阈值 | 含义 |
|---|---|---|
| DOM 变异次数 | 工作台 300 / 文件页 1500 / 其它 600–900 | 自激循环的直接特征 |
| 长任务（>50ms） | < 5 | 主线程被长任务占住 |
| 主线程延迟（5 次 setTimeout(0) 总耗时） | < 300ms | 页面"点不动"的量化 |
| 正文长度 | > 60 字 | 别白屏 |

实测（修复后）：6/6 通过，全部 0 变异、0 长任务、0ms 延迟。

**灵敏度验证**：把上一版带死循环的 index.html 挂成 `/__buggy.html` 再跑同一套断言 ——
变异 71,151 次、主线程延迟 1506 ms，**必然 FAIL**。说明这套阈值真能拦住回退，
不是摆设。

顺带补验了 7.19 之后加的「本盘版本占用」显示：
面板写「本盘版本共 4.0 MB · 7 个文件」，与 `/api/version-usage` 的
`bytes=4194304 count=7` 完全一致；该文件自己的版本行数 2 也与 `/api/versions` 一致。

另：`/api/version-usage` 加了缓存失效 —— 归档/删除后立刻反映，不用再等 60 秒缓存过期
（此前实测删除后数字不变，会让人误以为没删掉）。
