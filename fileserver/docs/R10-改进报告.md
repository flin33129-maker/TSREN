## 二、在线预览（乱码）到底坏在哪

预览原来只有一条路径：**把文件当文本读出来塞进 `<pre>`**。对 xlsx/docx 这类二进制文件，
这条路必然花屏；对中文 Windows 上常见的 GBK txt/csv，按 UTF-8 硬解同样是乱码。

分两层修：

1. **文档类走服务端渲染**：`.xlsx/.xlsm/.docx/.docm/.pptx/.pptm/.odt/.ods/.odp/.rtf/.pdf/.wps/.et/.dps`
   统一走 `/api/office/preview`，服务端用 LibreOffice 转 PDF 后以 iframe 内嵌。
   非文档扩展名请求该接口会得到 **415** 和"该格式不支持在线预览，请下载后用本地应用打开"。
2. **文本类做编码嗅探**：`TextDecoder('utf-8',{fatal:true})` 严格解码 → 失败退
   `TextDecoder('gb18030')` → 最后兜底宽松 UTF-8。GB18030 覆盖 GBK/GB2312，Chromium 自带，无需额外依赖。

顺带把转换做成**串行队列**：同一时刻只跑一个 LibreOffice 进程，避免大表格并发把内存打满；
超时从 120 秒放宽到 300 秒（3.3MB 的 xlsx 转出 184MB PDF 实测要 238 秒）；
失败时清理临时目录（原来只在成功时清理，失败会留垃圾）；缓存目录超过 512MB 或 7 天自动瘦身。

## 三、上传下载为什么会卡死，怎么变稳的

**上传**：前端原来每个文件发一次巨大的 multipart 请求，多个文件就是多个并发大请求，
既没有分片也没有重试，中途断一个就整批失败——表现就是"卡死"。

现在：
- 单文件 > 8MB 走服务端已有的分片接口：`/api/chunk-init` 开单 → 4 路并发 `PUT /api/chunk-data`
  （每片 8MB，指数退避重试 3 次）→ `/api/chunk-complete` 合并；
- 单文件 ≤ 8MB 时每 8 个一批 multipart 上传，减少请求数；
- 进度按字节汇总（最高 99%，全部完成才到 100%）。

**下载**：服务端本来就是 `fs.createReadStream` + `Accept-Ranges: bytes`（1MB 缓冲、支持 206 分段、
按客户端 IP 分桶限速），问题是 Nginx 侧的缓冲和超时——已调整 `client_max_body_size 0`、
`proxy_request_buffering off`、`proxy_read_timeout` 分级放宽，并把 systemd 的 `LimitNOFILE` 提到 65535。

实测（本机回环，最理想条件，主要用于验证"不崩不卡"而不是绝对速度）：

| 场景 | 结果 |
|------|------|
| 32MB 分片上传 | 1.0 秒，落盘字节数精确 33554432 |
| 12 个小文件批量上传 | 1.0 秒 |
| 64MB 全量下载 | HTTP 200，67108864 字节，0.28 秒，242 MB/s |
| 64MB Range 前 8MB | HTTP 206，8388608 字节 |
| 6 路并发下载 64MB | 484 ms |
| 15 路并发下载 64MB | 15 个请求全部 200，服务保持 active，Node RSS 354MB |

> 说明：真正的"多线程 P2P（比如 WebTorrent 式）"需要客户端之间互传，在浏览器里要占用额外端口与
> 权限，而且局域网内文件已经在同一台机器上，收益主要是"多台设备同时拉同一文件时省带宽"。
> 这一轮先把"不卡死、可续传、并发不崩"做扎实；P2P 分发更适合放进下一轮做成可选插件。

## 四、连接服务：补上 SMB

原来这一栏只有 WebDAV/S3/FTP/NFS/DLNA/mDNS，SMB 是缺的。补的时候踩了两个坑：

1. 判定"是否运行"不能只看进程存在：工作站以 `tokenllm` 身份运行，而 `smbd` 是 root，
   `process.kill(pid, 0)` 会抛 **EPERM**。如果把它当失败，就会误报"未运行"。现在 EPERM 视为存活。
2. 共享名不在 `/etc/samba/smb.conf` 里，而是通过 `include = /etc/samba/station-shares.conf` 引入。
   现在会递归跟随 `include`，排除 `[global]/[printers]/[print$]`，最多返回 16 个。

结果：`smb: true`，共享名 `公共盘 / 办公 / 备份 / 乱七八糟 / 数据 / Getea / K% / K1 / Q21`（9 个），
界面显示"运行中 · 公共盘 / 办公 / 备份 / 乱七八糟 等 9 个共享"。

## 九之一、收尾时又发现并修掉的两个问题

这两个不在你最初的清单里，是自检过程中暴露的真问题：

1. **LibreOffice 配置目录泄漏**：每次文档转换都会用
   `-env:UserInstallation=file:///tmp/lo-prof-<hash>` 新建一个约 290KB 的配置目录，
   原代码只清了输出目录，配置目录从来没人删 —— 转一次漏一次。
   现在转换回调里显式清理，并在每次转换前扫掉超过 1 天的孤儿目录（进程被强杀时兜底）。
   修复后连续转换，`/tmp` 下 `lo-prof-*` 与 `lo-*` 残留均为 0。

2. **分片上传接口对非法输入返回 500**：客户端若把文件名塞进 `path` 字段，
   服务端解出目录不存在，`open` 抛 ENOENT 后被兜成 `{"error":"服务器内部错误"}`，
   日志里只有原始堆栈。现在的行为：
   - `path` 末段等于 `name` → 自动退成父目录（兼容把完整路径塞进 path 的客户端）；
   - 目标目录不存在/不是目录 → **400**「目标目录不存在」并提示 path 应传目录；
   - 打开临时文件失败 → 400（ENOSPC/EACCES 用 507）并带具体原因。

另外清理了这一轮测试留下的所有痕迹：临时登录页、压测脚本、`_st*` 之类测试文件、
孤儿上传临时文件、回收站。
