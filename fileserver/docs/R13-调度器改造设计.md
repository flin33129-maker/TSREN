# 注入件统一调度器 · 改造设计

目标：消除「注入式 DOM 维护」与「React 列表刷新」的互相打扰。
现状问题：文件页 DOM 变异约 2000/3s（纯 React 页面约 8–13），主线程 0ms、无长任务，
**当前不影响流畅度**，但属于可观测的浪费，且随注入件增多会继续上涨。

---

## 一、现状盘点（文件页）

当前各自独立的维护循环：

| 组件 | 触发方式 | 频率 | 维护动作 |
|---|---|---|---|
| 文件类型色标 `.r13-ftype` | MutationObserver(全 body) + rAF | 页面变动时 | 给每行插入图标节点 |
| 信息条 `#r13-filesum` | MutationObserver + rAF | 页面变动时 | 重建/更新数字 |
| 批量浮条 `#r13-selbar` | MutationObserver + rAF | 页面变动时 | 显隐 + 计数 |
| 选中数标题 `(N)` | change/click + 1.2s 定时 | 事件/定时 | 改 document.title |
| 任务入口 `.r13-tasklink` | MutationObserver + rAF | 页面变动时 | 插入链接节点 |
| 筛选 chips | MutationObserver + rAF | 页面变动时 | 重建 chips（10 节点） |
| 筛选提示 badge | 1.2s 定时 | 定时 | 改文本 |

问题：
1. 每个组件各自 `requestAnimationFrame`，同一帧内可能重复遍历 DOM 多次；
2. 每个组件各自 `MutationObserver` 监听 body，回调数量随组件数线性增长；
3. 定时器与观察器并存，职责重叠。

---

## 二、目标架构

```
┌─────────────────────────────────────────────┐
│  SingleScheduler（单例）                     │
│  · 唯一 MutationObserver（监听 main）         │
│  · 唯一 rAF 队列（同帧合并）                  │
│  · 注册表：{id, dep: 'files'|'games'|'all',  │
│            run(): void}                       │
│  · schedule(): 标记脏 → rAF 一次批量执行       │
│  · 可见性感知：document.hidden 时不调度        │
│  · 冷却：同 id 300ms 内最多执行一次            │
└─────────────────────────────────────────────┘
         │ 统一运行
         ▼
   各组件只注册 run()，内部仍需"判等再写"
```

关键约束（沿用已有教训）：
- **判等再写**：所有 textContent/属性写入前比较旧值，避免自激循环；
- **不跨路由执行**：run() 内部首行判断当前 hash 是否属于自己负责的页面；
- **不读 localStorage**：缓存到内存，定时刷新（例如 15s），避免每帧解析 JSON；
- **可开关**：`window.__r13Scheduler.enabled=false` 可整体停用，便于排查。

---

## 三、落地步骤

1. 新增 `r13Scheduler` IIFE，提供 `register(id, dep, fn)` 与 `schedule()`；
2. 逐个改造现有组件：删除各自的 MutationObserver / rAF / setInterval，改为注册；
3. 每改造一个，跑对应功能测试（`ui_*_test.py`），确认行为不变；
4. 全部改造后跑 `perf_smoke_test.py`，目标：文件页变异从 ~2000 降到 <800；
5. 若某组件在调度器下行为异常，单独回退该组件，不影响其他。

---

## 四、验收标准

| 指标 | 现状 | 目标 |
|---|---|---|
| 文件页 DOM 变异/3s | ~2000 | <800 |
| 主线程卡顿 | 0ms | 0ms（不变） |
| 功能测试 | 全过 | 全过（不得回归） |
| 帮助面板/筛选/批量等功能 | 正常 | 正常 |

---

## 五、风险与回退

- 风险：调度器本身出 bug 会导致全部注入件失效（单点）。
- 缓解：保留 `enabled=false` 开关与逐组件回退；先在测试环境验证 3 轮再上线。
- 回退：`cp -f /opt/station/backup/index.html.<批次>-before public/index.html`

## 六、两次实施尝试的结论（2026-10-22，重要）

### 尝试 1（失败）
把调度器定义插在 `async function yk` 前（与所有注入件同一锚点），并把筛选提示迁移到
`register()`。现象：`window.__r13Scheduler === undefined`，页面注入件整体失效。

**根因**：插入顺序问题——筛选提示的 IIFE 在调度器定义**之前**执行，
`window.__r13Scheduler.register` 抛 TypeError；而这是**模块顶层代码**，
顶层抛错会中止该模块后续所有语句，导致调度器定义根本没执行。
（`node --check` 只验语法，发现不了执行顺序问题。）

### 尝试 2（半成功，仍回滚）
把调度器定义改到 module script 最前面（紧跟 `<script type="module">`），迁移调用加
`if (window.__r13Scheduler) ... else 旧定时器` 防御。现象：`registry()` 正常返回
`['filter-badge']`，但筛选提示**出现严重延迟**（8 秒仍未出现，之后才出现）。

**原因判断**：筛选提示属于「交互即时反馈」，需要随筛选动作立刻响应。而调度器有
300ms 冷却 + 依赖 MutationObserver/rAF，筛选切换本身是"卸载→重挂载"的多次 DOM 变化，
被节流吞掉后要等下一次定时器（1.2s）才补，实际观感明显变慢（"点击后过一会儿才出现"）。

### 因此：组件分类结论

| 类别 | 组件 | 处理方式 |
|---|---|---|
| 交互即时反馈 | 筛选提示、批量浮条、行高亮 | **保持轻量直连**，不纳入调度 |
| 稳定状态展示 | 类型色标、信息条、任务入口、选中数标题 | 可纳入调度 |

结论：调度器**不是万能的**，只适合"状态类、允许数百毫秒延迟"的组件。
按此分类重新规划，预计可把文件页变异从 ~2000 降到 ~1000 左右（一半收益），
风险远小于"全部迁移"。

## 七、状态：暂停（5 次尝试后）

| # | 尝试 | 结果/原因 |
|---|---|---|
| 1 | 定义与迁移同锚点 | 顺序错误：被依赖的 IIFE 先执行 → 顶层抛错 → 后续不执行 |
| 2 | 定义提前 + 防御迁移 | 注册成功，但交互组件响应延迟明显（8s 未出现） |
| 3 | 按唯一锚点迁移 | 锚点实际出现两次（与"任务回跳"组件代码相同） |
| 4 | 按函数位置替换 | 注册成功（registry 含 task-link），但组件未渲染 |
| 5 | 补「注册后立即执行一次」 | 仍不渲染，执行链路问题未定位 |

**决定**：暂停该改造。理由：
- 收益仅为 DOM 变异 2000→约 1000，**用户无感知**（当前主线程 0ms、无长任务）；
- 成本已消耗 5 个轮次，仍有未定位的执行链路问题；
- 每次尝试都需"构建→部署→验证→回滚"，属于高风险低回报。

**若未来重启**，建议顺序：
1. 先在**测试页面**（不部署）用 CDP 打断点/日志验证调度器 run() 是否真的调用组件函数；
2. 从**最简单的纯状态组件**（如选中数标题，无依赖容器）开始迁移，而不是依赖 `#r13-filesum` 的组件；
3. 每迁移一个，跑该组件的功能测试，确认渲染时序无回归。

**当前替代做法**：已删除废弃的死代码（95 批），保持现有直连实现；
变异偏高但不影响体验，作为已知技术债记录在案。
